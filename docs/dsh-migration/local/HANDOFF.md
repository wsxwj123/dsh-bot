## 4. 和预期不符的地方

1. **C10（仅记录）系统提示词字数和 VERIFIED.md 不同**：本机 0.2.0 是 6330 字（VERIFIED 6359），0.1.5 是 8246 字（VERIFIED 8276）；工具个数和工具说明字符数完全一致。
   - 已查明原因：出厂配置的系统提示词由四部分组成，分别是身份句、人设、一段固定的英文工具使用说明，以及最后一句 `Your working directory is <路径>.`。其中会随机器变化的只有这条路径。
   - 本机核对时隔离目录路径是 90 字符。在临时目录里按 facts.ts 原样重放 C10，路径 82 字符，两个版本都正好少 8 字。由此推算，云端当时的路径约 119–120 字符。
   - 新系统用"只留人设"（C9），不含这句，不受影响。
2. **C1 启动加握手耗时**：本机 0.2.0 为 2905 ms（第一次运行），0.1.5 为 1552 ms；VERIFIED 记的是约 1.2–1.3 秒。结论仍是"符合"，耗时只是观察值。
3. **real-03 新会话不回话**：两次（示例人设和 bot5）都一样。新会话第一条消息把"系统背景 + 摘要 + 最近原话 + 对方：问题"写在一条里，模型这一轮只发了 1 次请求，没有调用 reply，所以"回答提到豆豆/周三"记为否。这不能说明摘要接不上（摘要本身六项事实都有），说明新段开头的写法没能引导模型用 reply 回话。
4. **real-03 摘要超长**：645 字和 692 字，超过指令里"不超过 600 字"的要求。
5. **real-04 第一次运行没有触发压缩**：默认 `--extra 6000` 时阈值 8330，真实模型 20 轮只涨到 4877。报告里"没有发生压缩（即使估值已超过阈值）"是写死的文案，和数据不符，估值并没有超过阈值。
6. **real-04 重跑时，"保留 2000"也压缩了**：预期是"很可能一直不压缩"。两种保留量一旦开始压就每轮都压，但这有一部分是测试设置造成的：阈值只比人设高 1000，而摘要本身就有 1000 多 token，压完马上又超。窗口真按 1M、阈值按 80% 时，不会出现这种连续压缩。
7. **用量基线覆盖天数只有 1.0–4.4 天**：每个 bot 只有 1 个当前会话文件，更早的在 `*.jsonl.bak*` 备份里，脚本不统计备份。另外，经代理的 gemini 缓存命中率只有 8–12%，和方案里引用的"命中率 36–67%"差距大，可能和代理怎样回报缓存用量有关，本机没有进一步核实。
8. **deepseek-flash 的 real-01**：A（出厂+人设）首轮发了 2 次请求，其它配置都是 1 次，原因没查。

## 5. 偏离任务书的地方

- **仓库位置**：按用户要求放在当前目录下，即 `/Users/wsxwj/Desktop/claude/dshbot/dsh-bot-work`，不是 `~/dsh-bot-work`。命令里的路径都相应替换了。克隆用的是本机的 SSH 账户别名，直接克隆指定分支，效果和任务书的 https 克隆加 checkout 一样。
- **第 3 步多了一道审查**：先用 `npm install --package-lock-only --ignore-scripts` 只解析依赖、不安装，查出带安装脚本的包并看过内容，再按任务书原命令正式安装。最终的依赖树和直接安装相同。
- **第 6 步提前到第 5 步之前**，因为问题 10 要用盘点给出的别名。
- **盘点跳过了 `~/.dsh`**：`inventory.py` 默认会列出 `~/.dsh` 的 profile 名、会话数、有没有设置和凭据文件，这和铁律 3"不读写 ~/.dsh"冲突。经用户确认，用 `--dsh-home` 指向一个不存在的路径来跳过，并把那一行改写成"按铁律 3 未读取"。脚本仍对全局 dsh 和 claude 跑了 `--version`；事先在空的临时 HOME 下试过，这两条命令不会写任何文件。
- **盘点结果做了名字折叠**，因为仓库是公开的：
  - 人设和 access.json 的备份文件名含日期、改动说明、bot 真名或人设内容；
  - 会话目录 `memory/` 下的文件名描述了记忆主题；
  - launchd 任务名含系统用户名；
  - 旧仓库 `configs/` 里有一个以真名命名的配置文件，脚本没有替换成别名。
  - 以上都改成"个数 / 别名 / `<用户名>`"，数字没动。详见 INVENTORY.md 末尾。
- **补充计数**：为了解释基线覆盖天数短，额外以只读方式统计了每个 bot 会话目录里 `*.jsonl` 和 `*.jsonl.bak*` 的个数和大小，不读内容，结果写在 INVENTORY.md 末尾。
- **C10 诊断**：用一个不进仓库的临时脚本按 facts.ts 的 C10 原样重放了一次（假模型，不联网），以查明字数差异。
- **真密钥步骤**：
  - 密钥由用户在客户端终端面板里用 `read -rs` 输入；
  - `--persona` 传的是临时目录里一个指向 bot5 人设的符号链接，这样命令行和日志里都不出现真实目录名。
- **real-02 第一次失败，以及一次违反铁律 4 的失误**：
  - 失败原因：用户粘贴的密钥末尾带了不可见字符（读入长度 38，正常 35）。dsh 能容忍，但 real-02 第一部分用 bun 的 `fetch` 直接调接口时，bun 拒绝了这个请求头，报错为 `TypeError: Header '14' has invalid value: 'Bearer sk-***已脱敏*** '`，原文里带着完整密钥。
  - 失误：本机 AI 排查时把这段报错原文打印进了本机会话，违反铁律 4。日志随即脱敏并删除原件；其它日志、报告和实验目录检查过，都没有残留。已当场告知用户，是否作废这个密钥由用户决定。
  - 重跑时，改为从输入里只提取 `sk-` 开头的那一串，并核对长度后再用。没有修改脚本。
- **real-04 加跑一次 `--extra 1000`**：用的是脚本自带的参数，经用户同意。两份报告都保留：`real-04-0.2.0-sample.md` 是默认参数，`real-04-0.2.0-sample-extra1000.md` 是调低阈值后的结果。
