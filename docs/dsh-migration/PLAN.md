## 一、结论

1. **能换，固定开销基本可以归零。**
   - 用"只留人设"的配法，dsh 发给模型的只有三样：人设原文、我们自己的几个工具、对话本身（已逐字核对）。
   - dsh 自带的身份句、二十多个内置工具的说明、AGENTS.md 和 CLAUDE.md 的自动注入、技能目录、运行时上下文，全部可以去掉。
   - Claude Code 每次请求自带约 2 万 token 的固定开销，换成 dsh 后只剩我们自己的几个工具和一段运行规则，估计约 1.5 千。
2. **大头是对话历史，要我们自己管。** 推荐的做法：
   - 账本和摘要都由我们自己负责。dsh 的会话只当"这一段对话的缓存"。
   - 一段聊到预算上限，就让模型在原会话里写一份陪伴聊天格式的交接摘要（几乎全部命中缓存），然后换一个新会话。
   - 新会话开头放：长期记忆、摘要、未完成的承诺、最近几轮原话。
   - **不用 dsh 自带的压缩**。理由和实测证据见第四节。
3. **我们自己的账本是唯一真相。**
   - 收到的消息先落盘；发给模型、发给用户，每一步都记账。
   - 实测发现：失败重试、取消、进程被杀之后，dsh 都会把那条用户消息留在自己的历史里。如果照旧"失败就原样重发"，模型会看到两遍。
   - 新系统改用"补救提示"，或者"换新会话、用账本重建上下文"，保证每条消息在模型眼里只出现一次（3.3 节）。
4. **几个必须知道的坑**（都已实测，详见 VERIFIED.md）：
   - **0.2.0-rc.2 默认会把会话日志（含对话原文）随每个请求一起上传给 DeepSeek。** `DSH_TELEMETRY_DISABLED` 关不掉它，必须禁用 `session-log-deepseek` 这一行。0.1.5 默认是关的。
   - 两个版本默认都在每个请求里附带一份 3–4 千字符的插件清单。禁用 `plugin-package-inventory-deepseek` 行就去掉了。
   - 开着思考时，dsh 会把之前每一轮的思考内容原样放回历史。会不会按输入计费，要用真密钥测（real-02）。
   - dsh 估单条消息长度时按"4 个字符 1 个 token"算，中文被低估好几倍。结果是它的自动压缩在中文对话里要么一直不压，要么几乎每轮都压。
   - 人设里的 `{{user}}` 会让 dsh 直接报错，示例人设里就有一处。在两个花括号之间插一个不可见字符就行，模型看到的文字不变。这算技术处理，不改人设内容。
   - 今天重装 `0.1.5-rc.1`，子包拿到的是 rc.3，你机器上是 rc.2。新系统要用锁文件把整棵依赖树钉死。
5. **预算建议：每次请求的输入不超过 4 万 token，可以按 bot 单独设。** 你的人设约 1.5 万，剩下 2.5 万给记忆和对话。数字要你拍板（第九节问题 2）。
6. **版本建议：0.2.0-rc.2**，装在机器人专用目录，用锁文件钉死。理由：
   - 它是 npm 上当前的 latest，和你的桌面版同代。
   - 两个版本在新系统依赖的行为上离线核对一致。
   - 如果真密钥脚本显示它在缓存或用量上明显吃亏，就退回 0.1.5。

## 三、新系统长什么样

### 3.1 进程

```
每个 bot 一个"网关"进程（bun / TypeScript，取代 dispatcher.ts + worker-manager.ts）
 ├─ Telegram 收发（grammY，沿用现有依赖）
 ├─ 账本（sqlite；bun 自带，Python 也自带，不引入新依赖）
 ├─ 回合调度：每个聊天一条队列，一次只跑一轮
 ├─ 工具服务：MCP over HTTP，只听 127.0.0.1，每个会话一个地址和口令
 ├─ 本机接口：带口令，给 Python 脚本和 bot 之间互推用
 └─ 子进程：dsh --profile acp --patch <本 bot 的补丁层>
       ├─ 独立 DSH_HOME；环境变量白名单（不含 Telegram 令牌）
       └─ 每个聊天一个 dsh 会话（私聊、每个群各自独立），按"段"轮换

Python 周边（定时任务，基本保留）：主动消息、情绪、导演、朋友圈、记忆整理
  —— 读账本（只读），经本机接口投递
```

- **一个 bot 一个 dsh 进程**，原因是人设在 dsh 里是进程级配置。
- **一个 bot 的所有聊天共用这一个进程**，每个聊天一个会话，所以私聊和群聊天然分开。
- 不同聊天的轮次可以并行，并发上限可配，默认 2。

### 3.2 目录

```
~/.dsh-bot/
  harness/                 钉死版本的 dsh（package.json + 锁文件，随仓库提供）
  credentials.yaml         全部密钥，权限 600；dsh 和 Python 共用这一份
  bots/<bot>/
    channel/               人设与配置：CLAUDE.md、access.json、relationship.json（格式与现在完全相同）
    memory/MEMORY.md       长期记忆
    dsh-home/              这个 bot 专用的 DSH_HOME（会话、设置、补丁层）
    state/ledger.sqlite    账本
    state/api.key          本机接口口令（600）
    logs/                  轮转日志
```

- 和你日常用的 `~/.dsh`、旧系统的 `~/.claude` 完全分开。
- 新旧两套可以同时装着；回滚时旧数据原封不动（第七节）。

### 3.3 一条消息的一生（送达账本）

1. **收到**
   - 先写账本，才算收到。唯一键：真实消息用"聊天 id + 消息 id"，合成消息（追问、承诺到期、导演提示等）用 UUID。
   - 网关崩溃时，Telegram 会把还没确认的更新重发过来，唯一键负责去重。
2. **排队**
   - 同一个聊天一次只跑一轮。
   - 空闲时收到第一条，先等一个连发窗口，沿用现在的 5 秒 / 12 秒。
   - 正在回复时来的消息先攒着，这一轮结束后合并成一条。
3. **开一轮**
   - 先在账本里记下"哪几条消息、送进哪个会话的哪一轮"，然后才发给 dsh。
4. **一轮的结局**
   - **正常结束**：记账。有没有回复，看我们自己的发送记录，不看 stopReason（它把"被中止"也报成正常结束）。
   - **dsh 返回错误，进程还活着**：那条消息已经在 dsh 的历史里了（实测 C15），不能原样重发。
     - 先按错误类型等一会儿：限流、服务端错误要等；鉴权、余额问题直接通知你。
     - 然后发一句补救提示："⟦系统⟧ 上一条消息没能处理完，请接着回应对方上面那条消息"。
     - 最多重试 2 次。再不行就进死信，并通知你。
   - **dsh 进程死了**（崩溃、被杀、机器重启）：不知道那条消息进没进它的历史，所以不赌，直接**换一个新会话，用账本重建上下文**。这样每条消息在模型眼里只出现一次。代价是这一次缓存不命中。
   - **这一轮已经有回复发出去了**：不再重试。宁可少回一次，也不重复说话。
   - **一轮卡住**（超过 N 分钟没有任何进展）：先 `session/cancel`；取消不掉就重启 dsh，按"进程死了"处理。健康检查会把这种情况报出来。
5. **发送**
   - 模型调用 reply 工具，网关逐段发出，每段记账。
   - 工具返回值告诉模型"送达几段、第几段没送达、为什么"。
   - 引用的消息不存在时，去掉引用重发一次。
   - 被限流、等不起时，如实告诉模型"这几段没发出去，多久后可以再发"。已经发出去的段不受影响。

### 3.4 "段"、预算与摘要（记忆的核心）

**一段 = 一个 dsh 会话。** 段内照常累积，DeepSeek 的前缀缓存可以吃满：每轮新增的部分才算"未命中"。

**什么时候换段**

- 每轮结束看 dsh 回报的上下文大小（ACP `usage_update.used`）。它以供应商回报的用量为准：用假模型实测，和供应商回报的输入 token 每轮只差约 10 个（就是那一轮的输出）。real-04 会在真模型上再确认一次。
- 超过预算的 85%，就在这个聊天空闲时换段。
- 如果下一条消息很长、一进来就会超预算，就先换段再处理。

**怎么换段**

1. 在旧会话里发一条"整理记忆"指令，让模型按下面五个小标题写交接摘要：
   - 我说过的要紧话
   - 我答应过的事
   - 对方的情况
   - 正在聊的话题
   - 我们现在的关系和气氛

   这一轮所有工具都锁住，防止模型把摘要发给对方。这次请求的前缀就是刚才的对话，几乎全部命中缓存（real-03 会测命中率）。
2. 摘要为空或明显不像样，就保留上一份摘要，不覆盖。
3. 关闭旧会话，下一轮开新会话。新会话的第一条消息开头放：
   - 长期记忆
   - 最近一份摘要
   - 未完成的承诺（从承诺表取，不靠摘要）
   - 最近 K 轮原话（从账本取，包括 bot 真正发出去的话）

   后面才是这一轮的新消息。

**私聊和群聊一样处理。** 这同时满足"压缩之后把最近原话补回上下文，私聊和群聊都要"。

**跨会话共享事实：**

- 长期记忆。模型用 `remember` 工具写，定时整理任务再从账本补充。
- 某个会话新记了一条，其它活跃会话在下一轮收到一行简短提示。

**以 4 万预算为例：**

| 部分 | 大小（token） | 说明 |
|---|---|---|
| 人设 | 约 15,000 | 固定，每个请求都在最前面，跨会话也能命中缓存 |
| 运行规则 + 工具说明 | 约 1,500 | 固定 |
| 长期记忆 | ≤ 3,000 | 每段开头 |
| 近期摘要 | ≤ 1,500 | 每段开头 |
| 未完成的承诺 | ≤ 500 | 每段开头 |
| 最近原话 | ≤ 5,000 | 每段开头 |
| 段内新增对话 | 约 7,000–13,000 | 大约 15–30 轮后换段 |

**粗算成本（只是估计，M2 会实测）：**

- 段内每轮的输入在 2.6 万到 4 万之间，但"未命中"只有新增的几百 token。
- 换段那一轮多出约 1 万未命中（新段开头的记忆、摘要和原话），摊到每轮约 400–600。
- 对比你现在的部署：每次请求输入中位数 6.9–11.1 万，命中率 36–67%，也就是每次有 2–7 万 token 未命中。
- 新系统每轮未命中大约 1 千出头，命中部分也降到原来的一半以下。

### 3.5 模型能用的工具

每个会话挂一个 MCP 服务，地址和口令都只属于这个会话，网关据此知道是哪个聊天。

| 工具 | 作用 |
|---|---|
| `reply` | 发消息。目标聊天就是本会话所属的聊天，不能省略，也不会默认成"上一个聊天"。跨聊天发送要显式指定，并且受策略约束。参数沿用现在的 `text`、`reply_to`、`files`、`as_voice` 等 |
| `react` | 给消息加表情 |
| `stay_silent` | 明确选择不回复，并写明原因（原因不会发给对方）。这样"故意不回"和"忘了调 reply""被中止"就能区分开；后两种会补一句提示，最多一次。它取代旧系统的冷启动提醒 |
| `commitment_create` / `commitment_list` / `commitment_cancel` | 登记、查看、取消承诺 |
| `remember` | 写一条长期记忆 |
| `generate_image` | 生图（M4） |
| 朋友圈相关（点赞、回评论、发圈） | M4 |

**运行规则**放在人设后面，是一个单独的段，不改人设文件。大意如下，约 300 字：

> 你在 Telegram 上聊天。想让对方看到的话必须用 reply 发出，直接输出的文字对方看不到。可以按人设选择不回复，那就调用 stay_silent。以 ⟦系统 开头的内容是程序给你的说明，不是对方说的话。答应对方将来要做的事，用 commitment_create 登记。值得长期记住的事，用 remember 记下。私聊里的内容不要说到群里。

### 3.6 dsh 的配法与进程管理

**补丁层由网关生成，每个 bot 一份：**

- **人设**：`system-prompt` 行设 `includeHarnessIdentity: false`、`includeRuntimeContext: false`；`personaPrefix` 是人设原文（`{{` 转义），`personaSuffix` 是运行规则。
- **禁用的行**：
  - 全部内置工具；
  - `agent-instructions`、`skill`、`skill-filesystem`、`tool-skill`；
  - `session-log-deepseek`、`plugin-package-inventory-deepseek`、`session-telemetry-otel`；
  - `session-title-llm`、`mcp-resources`。

  完整清单见 `lab/dsh/lib/profile.ts`。
- **自带压缩**：关掉自动压缩（`auto: false`）。保底只留一层：真的撞上模型的上下文上限、请求被拒时，记一条告警，然后由我们换段。
- **会话文件**：用不压缩的格式，方便排查，也方便清理已经关闭的老会话。我们**不靠它判断送达**。

**进程环境**

- 只传白名单里的变量：PATH、DSH_HOME、LANG、TZ、`DSH_TELEMETRY_DISABLED=1`。
- 密钥只在 `credentials.yaml` 里，不在环境变量里，也不在命令行参数里。
- 自动化测试会断言：dsh 进程的环境里没有 Telegram 令牌。

**权限请求**一律自动拒绝。内置工具都关了，正常情况下不会出现权限请求；万一出现，记一条告警。

**进程管理**

- **单实例**：pid 文件同时记下启动时间和命令行。清理残留进程前要核对这两样，只按进程名匹配不算数（H-03）。
- **停止**：先关闭标准输入，等它自己退出；超时再发 SIGTERM，再超时才 SIGKILL。确认进程已经退出，才允许起新的（H-08）。
- **启动失败**：退避重试，每次重试前确认没有活着的实例；状态不会卡在"启动中"（H-04、H-09）。
- **需要重启的变更**（比如改了人设）：等所有聊天空闲才重启，不打断正在生成的回复；重启后自动补投积压的消息。

**换模型或供应商（只影响这一个 bot）**

- **换模型**：改 `configs/<bot>.yml` 的 `brain` 段，例如 `{provider: deepseek-official, model: deepseek-v4-flash, reasoning_effort: low}`。网关在各会话空闲时调用 `set_config_option`，下一轮生效，不重启进程。
- **换供应商路由或密钥**：写进这个 bot 的 settings 文件或共用的凭据文件，dsh 会热加载。
- 没有"全部重启"这个操作。

### 3.7 每轮送给模型的格式（示例）

私聊：

```
⟦10-05 周日 21:14 · 距上条 3 分钟⟧
今天好累啊
```

群聊。每轮带上自上次以来群里的新消息，被导演点名或被 @ 的那条标出来：

```
⟦21:14⟧ 小王：周末去爬山吗
⟦21:15⟧ 陈露露（你）：看天气吧
⟦21:16⟧ 小李 @你：露露老师去不去？
```

- 系统说明一律用 `⟦…⟧` 开头。用户正文里出现的 `⟦`、`⟧` 会被替换掉，防止伪造（H-27）。
- 关系提示和情境锚点只在变化时附带一行。

### 3.8 承诺（新功能）

- **登记**
  - 模型调用 `commitment_create(内容, 时间)`。时间可以是具体时刻，也可以是"起床后""一睁眼""下班后"这类相对说法，网关按作息表换算成具体时刻。
  - 电话里答应的事同样登记：通话结束后，对 bot 的发言做同样的识别。
- **兜底**
  - 每轮结束后，用规则识别 bot 实际发出的文字里有没有"许诺未来"：时间说法加承诺动词，比如"三点提醒你""明早叫你""晚点告诉你"。
  - 如果这一轮模型没登记：时间能解析的，自动补登记，并在下一轮告诉模型"已替你登记，不是承诺就取消"；解析不了的，下一轮提醒模型自己补。
  - 识别规则有单独的测试集。
- **到点**
  - 网关里的调度器每 30 秒检查一次。
  - bot 按作息在睡觉，就顺延到起床后，并在提示里说明迟了多久，不作废。
  - 到点时触发一个合成轮次："⟦系统·承诺到期⟧ 你答应过……（原话：……），现在……"。
- **算不算兑现**：以这一轮账本里有没有真正送达的消息为准。没开口不算，会退避重试；最多 3 次，然后标记失败，并通知你。

### 3.9 主动消息

- **每次机会都有结果，并按原因安排下一次**，不再先把周期重新随机、再判断：
  - 在睡觉：起床后再试；
  - 刚聊过：过 30–60 分钟再试；
  - 没素材：1–2 小时后再试；
  - 额度用完：下个窗口再试。
- **发朋友圈和私聊各走各的闸门，互不取消。**
- **投递走本机接口。** 只有真正送达才记额度。

### 3.10 后台模型任务（情绪、导演、裁判、签名、朋友圈文案、记忆整理）

- 这些本来就直连 DeepSeek，不经过 Claude Code，也**不需要经过 dsh**。直连更省，也更简单。
- 统一成一个 Python 客户端：指数退避；每个任务记连续失败次数，熔断后暂停；按 bot、按任务设日上限。
- 修两处无限重试：导演每 2 秒重试一次，情绪每 5 分钟无限重试。
- 密钥从共用的凭据文件读。

### 3.11 安全与日志

- **本机接口**
  - 只听 127.0.0.1，口令放在权限 600 的文件里，比较时用常量时间比较。
  - 拒绝带 `Origin` 头的请求，防浏览器里的网页跨站调用；只收 `application/json`。
  - 发文件只允许白名单目录（媒体下载目录和生图输出目录），防止把本机任意文件发出去。
- **清记忆类命令**：校验发命令的人是主人，并且 @ 的是本 bot。
- **日志**
  - 所有组件都落盘，单个文件超过上限就轮转（默认 10MB × 5 份）。
  - 写盘前统一脱敏：Telegram 令牌、`sk-` 开头的密钥、Bearer 口令。
  - 自动化测试会扫描日志，断言里面没有令牌。
- **语音令牌泄露**：把 httpx 的日志级别调到 WARNING。
- **隐私开关**：遥测、会话日志上传、插件清单三项都在补丁层里禁用，并有测试断言请求里不带这些字段。

### 3.12 健康检查

- **网关心跳**：主循环每 10 秒写一次心跳文件。外部看门狗（launchd 每分钟跑一次）发现心跳停了，就重启这个 bot。
- **dsh 存活**：每分钟用 `session/list` 探测一次，5 秒不回就算卡住。
- **"活着但不干活"**：网关 `/v1/health` 报告以下几项，超过阈值就判为不健康：
  - 每个聊天最老一条未处理消息的年龄；
  - 当前这一轮多久没有任何进展；
  - Telegram 最近一次成功拉取的时间。
- **通知**：不健康时，在恢复后给主人发一条"刚才卡了 X 分钟，已恢复，有 N 条消息补投"。

## 四、记忆方案三选一

任务书给了三种手段。我在两个版本上都实测了出厂压缩。

| | ① 声明较小的上下文窗口 + 出厂压缩 | ② 自己写压缩后端（继承出厂压缩，只改写摘要的那一步） | ③ 我们自己管历史，dsh 会话按段轮换（**推荐**） |
|---|---|---|---|
| 摘要内容能不能按陪伴聊天来写 | **不能**。指令写死成英文"编程助手检查点"，小标题是 `## Files and Code` 这类 | 能 | 能 |
| 预算能不能卡准 | **卡不准**。中文被按 4 字符 1 token 低估：保留量设大一直不压，设小几乎每轮都压（实测 C21） | 同样卡不准。摘要可以换，但选哪段去压、保留多少，还是出厂那套算法 | 能。我们看 dsh 回报的上下文大小（以供应商用量为准）自己决定什么时候换段、补回多少 |
| 缓存 | 每压一次，历史开头就变一次；如果频繁压，每轮都不命中 | 同 ① | 段内只在末尾追加，命中率高；换段时付一次未命中 |
| 压缩后补回最近原话 | dsh 会逐字保留最近一段，但保留多少受上面的低估影响；我们拿不到"什么时候压了"的通知（ACP 收不到压缩事件） | 同 ① | 天然就有：新段开头从账本补，私聊群聊都一样 |
| 对 dsh 内部接口的依赖 | 只用配置 | **依赖 dsh 插件内部接口**（继承类、调内部服务）。预发布版本没有兼容承诺，升级就可能坏 | 只依赖标准 ACP 协议和配置 |
| 崩溃恢复、去重 | 要另外设计 | 要另外设计 | 和账本是同一套机制（3.3 节）：dsh 会话本来就可以丢弃 |
| 实现量 | 最小 | 中 | 最大，但都是我们自己的代码，能测 |

**建议用 ③。** 另外保留一个应急开关：配置里可以把出厂压缩重新打开，作为万一的退路。默认关闭。

## 五、里程碑与验收

每个里程碑都有两部分验收：

- **自动化测试**：在没有 Telegram、没有真实模型的环境里跑。
- **真机清单**：交给你在自己机器上做。

测试的做法见第六节。

### M1 单个 bot 的私聊文字收发

**范围**

- 网关骨架：配置加载、`access.json` 闸门、Telegram 长轮询；
- 账本；
- 回合调度和连发合并；
- dsh 进程管理；
- ACP 客户端；
- 工具服务：reply、react、stay_silent；
- 分段发送和按段回报；
- 本机接口：口令、白名单；
- `/clear`（私聊、主人）；
- 日志：轮转、脱敏；
- 时区可配的时刻标注；
- 人设加载和 `{{` 转义；
- 钉死版本的 dsh 安装。

这一期每个聊天先用一个会话不换段，换段在 M2 做。

**自动化验收**

1. 发一条消息，收到回复；账本里收到、开轮、发送三类记录齐全。
2. 回复中连发 3 条，合并成 1 轮。
3. 在四个时刻强杀网关，重启后检查：不丢、模型不会两次看到同一条、用户不会两次收到同一句。以假模型收到的请求、假 Telegram 收到的发送为准。四个时刻是：
   - 收到后还没处理；
   - 已经送进 dsh；
   - 回复发出一半；
   - 回复发完还没记账。
4. 发送异常时各自的表现：
   - 引用的消息不存在：去掉引用重发；
   - 第 2 段被拒（400）：模型收到"第 2 段未送达"；
   - 429 要等很久：如实回报，不阻塞其它聊天；
   - 发文件失败：前面已经发出的段不会重复。
5. 假模型连续返回 500：退避，最多 2 次，然后进死信并通知主人，不会无限重放。
6. 假模型不回应：超时后取消、补救；健康检查报"活着但不干活"。
7. 本机接口：
   - 没有口令：401；
   - 带 Origin 头：403；
   - 不是 JSON：415；
   - /send 请求白名单外的文件：拒绝。
8. `/clear`：非主人发无效；@ 的是别的 bot 也无效。
9. dsh 进程环境里没有 Telegram 令牌；日志里没有令牌；日志按大小轮转。
10. 改了这个 bot 的模型：下一轮生效，没有重启 dsh 进程；另一个 bot 不受影响。

**真机清单**

- 装好钉死版本的 dsh。
- 用真令牌、真密钥起一个 bot，私聊十几轮。
- 回复途中 `kill -9` 网关，确认重启后不重复、不丢。
- 查日志里没有令牌。
- 换一次模型，看是否在下一轮生效。

### M2 记忆

**范围**

- 账本里的对话流水；
- 换段：预算判断、在会话里写摘要并锁住工具、组装新段开头；
- 长期记忆：迁移 `MEMORY.md`、`remember` 工具、整理任务改读账本；
- `chat_history.py` 改读账本；
- 私聊、群聊各自的会话；
- `/clear` 遇到空摘要不覆盖；
- （可选）旧对话导入，见第九节问题 7。

**自动化验收**

1. 用假模型聊 200 轮：每个请求的输入都不超过预算（以假模型收到的请求计）；换段次数和预期一致。
2. 换段那一轮：工具被锁；摘要进了新段开头；新段开头的"最近原话"和账本一致，并且包含 bot 真正发出去的话。
3. 崩溃后换新段：新段开头里每条消息只出现一次。
4. 私聊会话的请求里，从来不会出现群聊的话；反过来也一样。
5. 摘要为空时，不覆盖上一份。
6. `chat_history.py` 原有的各个函数，对账本给出的结果格式不变（沿用并改写原有单测）。

**真机清单**

- 跑 real-03。
- 连续聊一两天，从日志里看每轮的输入 token 和命中率。
- 聊到换段，确认 bot 不失忆。

### M3 承诺与主动消息

**范围**

- 承诺表和三个工具；
- 许诺识别兜底；
- 到点调度；
- 作息顺延（新写"何时醒来"）；
- 兑现判定；
- `self_initiate` 和 `life-context` 的两个缺陷；
- 主动消息投递改走本机接口；
- 心情与好感（用户决定并入 M3）：关系提示、情境锚点、被晾追问、积温情绪改读账本。

通话里的承诺挪到 M4，和电话一起接入。

**自动化验收**

1. 中文时间说法解析：50 条以上用例，覆盖"下午三点""明早""一睁眼""起床后""半小时后""周五晚上"等。
2. 许诺识别：正反例测试集。漏登记时会补登记，或者提醒模型补。
3. 用假时钟：到点时 bot 在睡觉，顺延到醒来后，提示里写明迟了。
4. 到点那一轮没有真正发出消息，不算兑现；重试有上限。
5. 主动消息：每种跳过原因对应的下次时间都正确；发朋友圈不会取消私聊。
6. （挪到 M4）通话摘要里有 bot 自己说的话；通话里的承诺进了承诺表。

**真机清单**

- 对 bot 说"下午三点提醒我……""明早叫我起床"。
- 夜里设一个提醒，看它醒来后有没有补上。

### M4 语音、生图、朋友圈、管理台

**范围**

- 语音进出：转写移出主路径；合成由网关发送。
- 通话：挂断后的摘要两边的话都要；电话里答应的事登记成承诺（从 M3 挪来）。
- `generate_image` 工具。
- 朋友圈工具，加私密圈过滤。
- `/hub` 换模型来源重做。
- voice-bridge 日志修正。
- 图片输入：模型支持看图就直接附图，不支持就先转成文字描述，或提示"看不到图"。

**自动化验收**：各条链路用假服务端到端跑通；私密圈不会出现在别的 bot 的上下文里；日志里没有令牌。

**真机清单**

- 发语音、收语音；
- 让 bot 发一张自拍；
- 网页上评论 bot 的朋友圈；
- 在 /hub 里给一个 bot 换模型。

### M5 多 bot 与群聊

**范围**

- 群聊会话；
- 导演改走接口、改读注册表、加退避；
- bot 互推加口令；
- 群聊记录；
- 多 bot 安装。

**自动化验收**：两个网关加一个假 Telegram 群：

- 导演点名后，被点名的 bot 能看到其他 bot 刚说的话；
- 预算锁、"闭嘴"锁生效；
- 群里的话不会进私聊会话；
- 互推没有口令会被拒。

**真机清单**：两三个 bot 拉进同一个群，跑一晚上。

### M6 切换文档

- 迁移脚本：复制人设、配置、记忆、关系数值；可选导入旧历史。
- 切换和回滚手册。
- 故障排查表。
- dsh 升级流程：改锁文件 → 跑离线核对 → 跑真密钥脚本 → 逐个 bot 切换。

如果你要继续支持 Windows，在这之后再加一个 Windows 里程碑。

## 六、测试怎么做

- **假 Telegram**：一个本机 HTTP 服务，实现 Bot API 里我们用到的那些方法（getUpdates、sendMessage、sendPhoto 等）。
  - 能按剧本制造各种故障：引用的消息不存在、429 限流、403、请求发出后断开连接（"可能已送达"）。
  - 能记录收到的每一次发送。
- **假 ACP 服务**：一个按剧本行事的 ACP 服务端。
  - 能调用我们的 MCP 工具、报错、卡住、崩溃，用来确定性地测回合调度和恢复逻辑。
- **真 dsh + 假模型**：`lab/dsh/lib/fake-llm.ts` 已经能同时说两种协议。
  - 集成测试直接拉起真 dsh，验证补丁层、隐私字段、工具挂载在真实 harness 上成立。
  - 本机没装 dsh 时，这部分自动跳过。
- **断言只看外部可观察的结果**：假 Telegram 收到了什么、假模型看到了什么、账本里是什么。不 mock 网关内部模块，也不断言"某个函数被调用过"。
- **Python 侧**：沿用现有 pytest。数据来源换成测试用的账本文件；投递换成假的本机接口。

## 七、切换与回滚

**新旧两套能并存**：目录不同，端口不同，状态不同。唯一的冲突是：同一个 bot 令牌，同一时刻只能有一个程序在收消息。

**按 bot 逐个切换：**

1. 停掉这个 bot 的旧 dispatcher。
2. 跑迁移脚本，把人设、配置、长期记忆、关系数值**复制**到 `~/.dsh-bot/bots/<bot>/`。只读旧数据，不改。
3. 可选：导入旧对话。从旧的 Claude Code 会话文件里取出用户的话和 bot 真正发出去的话，写进账本，再生成一份初始摘要。
4. 启动新网关，按真机清单抽查。
5. Telegram 会把旧程序还没确认的消息投给新网关，账本负责去重。

**回滚：**

1. 停掉新网关。
2. 启动旧 dispatcher。旧数据原封未动，直接接着用。

新系统运行期间的对话不在旧会话里。如果需要，可以从账本导出一份文本给你。

## 十、确认后的修订（2026-10-06，优先于前文）

依据：`docs/dsh-migration/local/DECISIONS.md`、`HANDOFF.md` 和 `reports/` 下的真密钥报告。

### 10.1 真密钥验证改变了哪些估计

| 项 | 原先的估计 | 实测（dsh 0.2.0-rc.2） |
|---|---|---|
| 人设成本 | 约 1.5 万 token | bot5 人设 16515 字，"只留人设"首轮输入 **8882** token |
| 出厂配置额外开销 | 5000–7000 | 5471–5472 |
| 上一轮的思考是否计入输入 | 待测 | **不计入**。三种接口写法下差值都是 0，开着思考不会让历史变贵 |
| 自己写摘要那次请求的缓存命中 | ≥ 80% | 示例人设 92%，bot5 98% |
| 摘要质量 | — | 五个小标题齐全，6 项事实全保留；实际说过的话被原样引用；"没答应"也如实记下了 |
| `usage_update.used` 是否可信 | 待测 | 等于本次请求的输入 + 输出，和 DeepSeek 回报的逐轮对得上，可以直接拿来控预算 |
| 出厂压缩 | 不适合 | 真触发后写出的是英文"编程助手检查点"，压完下一轮只有人设部分命中缓存 |
| 旧部署基线 | 中位数 6.9–11.1 万 | 4 个 bot 输入中位数 6.6–9.6 万，P90 9.3–14.4 万；经代理的 gemini 命中率只有 8–12% |

### 10.2 预算：按模型的上下文窗口，用到 80% 换段

- 每个 bot 的预算 = 它当前所用模型的上下文窗口 × 80%。DeepSeek 模型在 dsh 里登记的窗口是 100 万。
- 窗口大小从 dsh 回报的 `usage_update.size` 读取，不需要手填。
- 到线后按第四节方案③自己换段。dsh 自带压缩只作应急开关，默认关闭。
- 另外留一个可选的硬上限 `brain.max_input_tokens`。默认不设，你哪天想按成本收紧，改这一个数就行。

### 10.3 范围与平台

- **第一期 M1–M5 全做**，M6（切换文档）放最后。
- **每一期都兼顾 Windows**，具体做法：
  - 代码里不用 POSIX 专有的东西：dsh 用 `node <dsh 主包>/lib/bin.js` 直接拉起，不走 `.cmd` 外壳；停进程在 Windows 上用 `taskkill`；路径一律用 `path` 模块拼。
  - 仓库里加 GitHub Actions：在 Ubuntu、macOS、Windows 三个系统上跑全部自动化测试。测试只用假 Telegram 和假 ACP，不需要任何密钥。
  - 每期的真机清单里加 Windows 一项（需要你有台 Windows 机器，或者先跳过这一项）。

### 10.4 供应商：第一期就支持非 DeepSeek

- 旧部署多数 bot 用的是经本机 provider-proxy 转接的 `gemini-3.8-flash-high`。
- 新系统在 M1 就支持按 bot 配置 dsh 的 `llm-pi-ai` 路由，协议可选 `anthropic-messages`、`openai-completions` 等，地址和模型名都写在配置里。你的 provider-proxy 原本服务 Claude Code，应该说的是 Anthropic Messages 协议，可以直接接上。
- 默认模型按你的选择用 `deepseek-flash`。
- **需要你补一个信息**：provider-proxy 的地址，以及 gemini 模型的上下文窗口。M1 真机验收时再填就行。
- 已查到（M1 真机验收，见 `docs/dsh-migration/M1.md` 第五节）：proxy 在 `127.0.0.1:8770`，Anthropic Messages 和 OpenAI 兼容两种协议都支持，模型名 `gemini-3.8-flash-high`。还缺访问密钥和上下文窗口。

### 10.5 版本

- 用 0.2.0-rc.2。仓库新增 `harness/`（`package.json` + 锁文件），安装脚本把 dsh 装到 `~/.dsh-bot/harness/`。
- 锁文件和你本机生成的那份版本完全一致，只是下载地址用 npm 官方源；你那份指向 npmmirror，校验值相同，装哪一份都行。

### 10.6 答复本机 AI 交接说明里的问题

1. **按窗口预算时，崩溃后补回多少原话？**
   - 不按预算补满。
   - dsh 进程死了以后，先用账本里这一段的完整流水，单独请求一次模型写摘要。新段开头放：长期记忆 + 这份摘要 + 最近原话。最近原话默认上限约 8000 token，可配。
   - 正常换段时，摘要在旧会话里写，能吃到缓存；崩溃时旧会话用不了，只能单独写，但崩溃很少发生。
2. **新段开头 bot 没回话（real-03 两次都是）。** 两处改动：
   - 背景和新消息分成同一个 prompt 里的两个内容块。新消息用和平时完全一样的格式，不再写成"对方：……"夹在背景里。
   - 这一轮既没调 `reply` 也没调 `stay_silent` 时，补一句提示，最多一次。方案 3.5 节本来就有这条兜底，real-03 的测试脚本没带它。

   M2 做完后会再跑一次 real-03 验证。
3. **迁 30 天旧对话。** 迁移脚本（M6）会：
   - 读当前会话文件和全部 `*.jsonl.bak*` 备份，按记录 id 去重，只取最近 30 天；
   - 用户的话来自用户消息，bot 的话来自 reply 工具调用里的 `text`；
   - 同时读 `chats/*/voice_log.jsonl` 和 `group_transcripts/`。
4. **非 DeepSeek 供应商**：第一期支持，见 10.4。
5. **Windows 的测试和 CI**：见 10.3。
6. **real-04 的两个小问题**：已修。结论文案改为按数据判断；默认 `--extra` 从 6000 降到 1500。
7. **旧部署的状态文件**（`.promises.json`、`.hang-state.json` 等）：按你"不参考实现"的决定，不读它们的内容。唯一可能要迁的是 `.promises.json` 里还没兑现的承诺，到 M6 时先问你要不要迁。
