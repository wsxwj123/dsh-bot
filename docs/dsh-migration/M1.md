## 一、这一期做了什么

| 功能 | 怎么做的 |
|---|---|
| 收消息 | 长轮询。每条消息先过 `access.json` 白名单，再和 Telegram 的 offset 在同一个事务里写进账本。崩溃后 Telegram 重发同一条，靠唯一键去重 |
| 已读 👀 | 沿用旧系统：白名单内的私聊消息收到就加 👀 |
| 连发合并 | 空闲时等 5 秒没有新消息再处理，最长等 12 秒；回复途中来的消息，这一轮结束后合成一轮 |
| 每轮的格式 | `⟦10-05 周一 晚上 21:14 · 距上条约 3 小时 · #1234⟧` 加正文。时区可配。用户正文里的 `⟦ ⟧` 会被换掉，防止伪造系统说明 |
| 模型的工具 | `reply`（分段发送，逐段回报送达情况）、`react`（表情）、`stay_silent`（明确选择不回，写原因） |
| 分段发送 | 每段先记"打算发"，发完记结果。引用的消息不存在就去掉引用重发；某段被拒，告诉模型"第 N 段未送达"，其余段照发；被限流且等不起，如实告诉模型多久后能再发 |
| 模型报错 | dsh 还活着：等一会儿，发一句补救提示（不重发原文），最多 2 次；还不行就放弃并通知你。密钥、余额、模型名这类错误不重试，直接通知你 |
| 卡住 | 一轮 3 分钟没有任何进展就取消；取消不掉就重启 dsh，换新会话补上 |
| dsh 进程死了、网关被强杀 | 不赌消息进没进 dsh 的历史：作废这一段，开新会话，开头用账本里最近的原话补前情。已经有回复发出去的，不再重试 |
| 换模型 | 改 `~/.dsh-bot/configs/<bot>.yml` 的 `brain` 段，5 秒内被发现，下一轮生效，不重启 dsh，不影响别的 bot |
| 改人设 | 等所有聊天空闲时重启 dsh，会话续上，不打断正在生成的回复 |
| `/clear` | 只有主人能用；`/clear@别的bot` 无效。效果是开一个新会话，清空前的内容不再带进去 |
| 本机接口 | 只听 127.0.0.1；要口令（`state/api.key`，权限 600）；带 Origin 头拒绝；只收 JSON；发文件只允许 bot 的 `media/` 目录 |
| 日志 | `logs/gateway.log`（事件，不含聊天正文）、`logs/chat.log`（对话流）、`logs/dsh-stderr.log`。10MB 轮转、保留 5 份，写盘前统一脱敏 |
| 健康 | 每 10 秒写心跳文件；`/v1/health` 报 Telegram 多久没拉到、每个聊天最老一条消息等了多久、当前这一轮多久没进展 |
| 隐私 | dsh 的会话日志上传、插件清单、遥测都关了；dsh 进程只拿到白名单里的环境变量，没有 Telegram 令牌；bot 目录权限 700 |

人设只做了技术处理：`{{` 中间插了一个不可见字符（dsh 会把 `{{…}}` 当模板变量报错），文字本身一个字没改。运行规则作为单独一段放在人设后面。

**这一期还没有的**（按计划在后面的里程碑做）：记忆和换段（M2）；承诺、主动消息（M3）；图片、语音、生图、朋友圈（M4，这一期图片和语音只给模型一个"[图片]""[语音消息]"占位）；群聊、多 bot 互动（M5）；开机自启和看门狗服务、旧数据迁移（M6）。

## 三、真机清单（请在你的 Mac 上用 bot5 做）

需要：bun、node（你机器上都有）、bot5 的旧目录、DeepSeek 密钥。全程不需要把任何密钥贴出来。

**0. 先停掉旧系统里的 bot5。** 同一个令牌同一时刻只能有一个程序收消息。没停的话，新网关的 `gateway.log` 会出现 `telegram.conflict`，健康检查也会提示。

**1. 装钉死版本的 dsh**（在仓库根目录）

```bash
bun gateway/scripts/setup.ts harness
```

预期最后一行：`✅ dsh 已安装：0.2.0-rc.2`。

**2. 准备密钥文件**

```bash
bun gateway/scripts/setup.ts credentials
open -e ~/.dsh-bot/credentials.yaml    # 把占位文字换成你的 DeepSeek 密钥，保存
```

**3. 准备 bot5**（只复制，旧目录不动）

```bash
bun gateway/scripts/setup.ts bot bot5 --from ~/.claude/channels/<bot5 的目录名>
bun gateway/scripts/setup.ts check ~/.dsh-bot/configs/bot5.yml
```

预期 `check` 最后一行是 `全部就绪。`

**4. 启动**

```bash
DSH_BOT_LOG_CONSOLE=1 bun gateway/src/main.ts --config ~/.dsh-bot/configs/bot5.yml
```

另开一个终端看对话流：`tail -f ~/.dsh-bot/bots/bot5/logs/chat.log`

**5. 逐项试**

| 做什么 | 预期 |
|---|---|
| 私聊 bot5 十几轮，其中几次连发两三条 | 每次都回；连发的几条合成一次回；回复风格和以前一致 |
| 让它说一段长的（比如"讲讲你今天做了什么，多说点"），在它分段发出的途中，另一个终端执行 `pkill -9 -f 'gateway/src/main.ts'`（模拟断电），然后重新执行第 4 步 | 已经发出的段不会再发一遍；还没开始回的消息，重启后会补上回复 |
| 发 `/clear` | 收到"【系统】已清空这段对话的上下文"；下一条消息它不记得清空前聊的内容 |
| 改 `~/.dsh-bot/configs/bot5.yml` 里的 `model:`（比如改成 `deepseek-v4-pro`），等 5 秒再发一条 | 照常回复；`gateway.log` 里出现 `brain.applied`，模型是新的；`health.ts` 显示 dsh 还是"第 1 次启动" |
| 运行 `bun gateway/scripts/health.ts --config ~/.dsh-bot/configs/bot5.yml` | 显示"健康" |
| （可选，有 Windows 机器时）在 PowerShell 里做第 1–5 步，路径换成 `$HOME\.dsh-bot\…`，强杀用 `Stop-Process -Force -Id <pid>` | 同上 |

**6. 贴回来这三样**（都只有数字和"有 / 没有"，不含聊天内容和密钥）

```bash
bun gateway/scripts/setup.ts check ~/.dsh-bot/configs/bot5.yml
bun gateway/scripts/health.ts --config ~/.dsh-bot/configs/bot5.yml
bun gateway/scripts/report.ts --config ~/.dsh-bot/configs/bot5.yml
```

`report.ts` 里重点看两行：

- "同一轮里同一句话发了不止一次"应该是 0。
- "日志里有没有机密"应该是"没有发现"。

**试完想切回旧系统**：在第 4 步的终端按 Ctrl+C 停掉新网关，再按你平时的方式启动旧的 bot5。新系统没碰旧文件，切回去什么都不用改。

## 四、这一期的新发现

- **换模型时，dsh 会往历史里插一条英文说明**：`[model changed: assistant turns above this point were generated by X; the session continues with Y]`，位置在那一轮用户消息的后面。只在真的换模型那一轮出现一次，几十个 token，对聊天没有影响，记录在案。
- **真 dsh 上逐字核对过**：系统提示词就是人设原文加运行规则；工具只有 `mcp__tg__reply`、`mcp__tg__react`、`mcp__tg__stay_silent` 三个；请求里没有 `dsh_session_log` 和 `dsh_plugin_packages`。
- `setup.ts harness` 按锁文件实装，dsh 报版本 0.2.0-rc.2。装的包数各系统略有不同：Linux 上 543 个，你的 Mac 上 540 个。差的是只在某些系统上才装的可选包，锁文件本身是同一份。
- **网关被强杀时，dsh 什么时候退出**：
  - dsh 空闲时，网关一死它半秒内就退出。
  - dsh 正在处理一轮时，它会先把这一轮做完。这期间它调用我们的工具都会失败，所以发不出任何消息，只可能多花一两次模型请求。
  - Windows 上，子进程不会因为父进程退出而结束。
  - 所以网关每次启动时，都会先按 pid 文件核对命令行，清理掉上次留下的 dsh。这一点在 Mac、Linux、Windows 的测试里都有验证。

## 六、真机验收后修的问题

| 报告里的问题 | 处理 |
|---|---|
| 1. 同一轮里，模型把同样的话又发了一遍（不是网关重发，是模型自己调了两次 reply） | 网关拦住：这一轮已经发过的段不再发。一次 reply 里大半段落都重复，就整次不发，并告诉模型"对方已经看到了"。另外，reply 成功后的回执改成"对方已经看到了，说完了就直接结束这一轮，不要把同样的话再发一遍" |
| 2. 新会话第一轮偶尔不回话，要靠提醒 | 每个新会话的第一轮，在新消息前面加一句很短的提醒（用 reply 回复，或者调用 stay_silent），每个会话只出现一次。原来的兜底提醒保留 |
| 3. 被强杀打断的回复不会补完 | 仍然不自动重发，防止重复。但下一轮的新会话里会写明"你上一条回复本来要发 N 段，对方只收到了前 M 段"，由模型决定要不要自然地补上 |
| 4. 日志里 `seeded` 字段会误导 | 改成 `segment.seed` 事件，记录实际补了几条前情、有没有被打断的回复 |
| 5. 已经回复了，又调用 stay_silent | 这一轮已经有回复送达时，stay_silent 不生效，只告诉模型"已经回复过了"；先说不回、后来又回了的，也不再算"沉默" |
| 6. `setup.ts check` 认不出别的占位文字 | 改成看密钥的格式：DeepSeek 密钥要以 `sk-` 开头、长度够，自定义路由的密钥不能有空格和尖括号。只报"像 / 不像"，不显示内容 |
| 7. 包数 540 和 543 不一样 | 见第四节，各系统的可选包不同，不是问题 |
| Windows 上的 3 项测试失败 | 两项是测试写法问题：一项检查得太早，一项是 Windows 路径里的冒号把测试指令截断了。另一项见第四节：强杀后的旧 dsh，改为网关启动时就清理，不等下一条消息 |
