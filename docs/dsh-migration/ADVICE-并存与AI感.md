# 并存与「AI 感」：两条建议

这份文档只讲两件事：新旧两套系统一起跑的时候要注意什么；角色 bot 聊久了为什么会不像原来那个角色、能做点什么。只写建议，不改代码。文档里不出现密钥、聊天内容、人设内容、账号信息。

## 一、新旧两套一起跑的时候

新旧两套可以装在同一台机器上跑，目录、端口、状态都是分开的。唯一的硬冲突是：**同一个 bot 的令牌，同一时刻只能有一个程序在收消息**。所以切换要按 bot 一个一个来，每切一个都能单独退回去。Telegram 会把旧程序还没确认的消息重新投给新网关，账本会去重，不会重复回复。

### 哪些共用文件不能两边同时改

- **供应商文件 `providers.json` 和凭据文件 `credentials.yaml`**（在 `<根>` 下，默认 `~/.dsh-bot`）：所有新系统 bot 共用。自建供应商的地址、格式、模型、密钥键名在 `providers.json`，密钥值在 `credentials.yaml`。一个 bot 在改的时候，别的 bot 不能同时改同一份——详见下面"为什么要加锁"。
- **朋友圈库 `state.db`**：新旧两套共用这一份。两套的朋友圈网页不能同时开着——一个库里同一时刻只能有一个写入者，双开会互相顶、重复发。要等全部 bot 都切完、把旧的朋友圈网页停掉，再用新仓库的脚本重装。
- **`configs/_global.yml`**：全部切完、换共用服务时，从旧仓库拷一份到新仓库；别两边同时改。
- **每个 bot 的频道目录**（令牌 `.env`、`access.json`、人设、长期记忆）：新 bot 的这些文件是从旧目录**复制**过来的，旧目录原样保留、别删。同一个令牌仍然只能一个程序收。
- **群聊记录 `groups/*.jsonl`**：所有 bot 共用一份追写，导演也读它。群聊要用的话，先停旧的导演，它还在给旧 bot 点名。

### 为什么要加锁

`providers.json` 和 `credentials.yaml` 的写入都是"**读出整份 → 改一处 → 整份写回**"。如果两个 bot 同时做这件事，后写的会把先写的那次改动整个覆盖掉：轻则对方刚加的供应商没了，重则把刚删掉的又"复活"回来，或者两个 bot 抢同一个密钥键名。

所以改这两个文件前要先抢到一个共用的小锁（`providers.lock`），保证同一时刻只有一个 bot 在改。拿到锁之后，它会**重新读一遍文件**再改、再写，确认中途没有被别人动过。几个要点：

- 拿到锁的 bot 只做"重读 → 改 → 写"，通常是一瞬间的事，**不在锁里联网**（拉模型列表是在锁外面先做完的），所以等锁一般很快。
- 等不到锁会报"别的 bot 正在改供应商，请稍后再试"，重试即可。
- 锁文件如果残留（改文件的进程崩了没删掉）：会看持锁的进程还在不在，或者锁是不是已经太老（超过固定的一小段时限），是残留就当没锁清掉，重新抢。
- **手动编辑这两个文件之前**，先确认没有引导正在保存（比如正在输密钥、正在刷新模型），免得两边的改动互相覆盖。

## 二、「AI 感」：为什么角色会走形

### 上下文里到底有什么

每一次要模型回话，程序按固定顺序把下面这些内容一起给它（前面的固定在前，后面的越来越长）：

1. **人设**：你的角色设定原文，放在最前面的系统提示里（程序不改动它的一个字）。
2. **运行规则**：紧跟在人设后面的一段程序说明——用什么工具发消息、怎么记东西、`⟦…⟧` 包起来的是程序的话不是对方说的，等等。
3. **工具说明**：每个工具（回话、不回话、表情回应、记事、生图、朋友圈、承诺提醒……）各自的用法说明。
4. **新会话开头的前情**：分三块——它的长期记忆、上一段的交接摘要、最近的一段原话。
5. **之后的历史**：会话开着的时候，之前对方说的、它回的、程序加的提示，都留在会话里，一轮一轮越滚越长。
6. **当轮还要临时附几行"生活状态"**：关系数值的提示、它此刻在干什么、被晾之后迟到的反应、群里近况。
7. **最后**才是对方当轮发来的新消息。

### 为什么会走形

- **人设被"稀释"**：对话越长，人设和运行规则在整段上下文里占的比重越小，模型注意力被最近的你来我往占满，语气、分寸、边界感就容易漂。这是长上下文模型的通病，不是程序出错。
- **顺着惯性走**：会话里历史一多，模型倾向于接着最近几轮的调子说，最早设定的人设就压不住。
- **换模型/换段即换风格**：换到另一家供应商、或换了模型，用的其实是另一个模型，写出来的风格本就会变；换段后的新会话只带着摘要开始，细节比原来少。
- **上一段的东西可能跟过来**：上一段里没清干净的思考内容或工具痕迹，也可能带到新一段。

### 几种缓解办法，各自代价

1. **换更强的模型**。
   好处：更会听指令、更稳得住人设。
   代价：更贵、可能更慢；不同供应商/模型的能力、能不能用工具、密钥都不一样，要一个能用的接口；换到另一家会触发换段（先写一份交接摘要再开新会话），换的当下风格会变一次。

2. **给会话设用量上限，让它定期换新会话**。
   好处：到一定用量就换段，新会话带着摘要和最近原话重新开始，等于把人设重新顶到前面，把"惯性"清掉。上限越小换得越勤。
   代价：每次换段要多花一次写摘要的模型调用（时间 + 钱）；摘要只留要点，细枝末节会丢；换得太勤反而显得记性差、接不上话，所以阈值不能设太小。

3. **改写人设的写法**。
   好处：把最要紧的说话方式、边界、口头习惯写得更短、更具体、更显眼，比一大段背景描述管用。
   代价：要人工反复打磨、试错；改人设会让正在用的会话换段（会话指纹变了）；改的是你本人的角色设定，得你自己来定。

4. **需要时再加"每轮附几行人设要点"的小功能**。
   做法：在每轮消息前再贴几行人设要点，把角色又拉回眼前。
   代价：要改代码；每轮都多花 token，长期下来是笔明账；要点和正式人设是两份，容易不同步，要有人维护。

这几条可以叠加。建议先试**不改代码**的那几条（换更稳的模型、把换段阈值调小一点、打磨人设写法），都不够用再考虑第 4 条。
